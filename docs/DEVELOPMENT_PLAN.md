# План разработки HydroCrack Insight

Основной ориентир - техническое задание из ЛР5. Приложение развивается как
desktop-система на Python и PyQt.

## 0. Подготовка проекта

Цель: развернуть репозиторий локально, создать безопасную ветку разработки и
подготовить базовые проверки.

Критерии готовности:

- код находится в рабочей папке проекта;
- создана ветка `desktop-tz5-development`;
- README описывает desktop-формат, установку, запуск и проверки;
- добавлены документы с планом и покрытием требований;
- есть baseline-тесты для ключевой доменной логики;
- синтаксическая проверка и baseline-тесты проходят.

## 1. Приведение структуры к ТЗ

Цель: явно разделить приложение на подсистемы из ЛР5.

Работы:

- уточнить пакеты для мониторинга, оборудования, ресурсов, отчетов,
  прогнозирования, пользователей и журналирования;
- выделить сервисы предметной области отдельно от UI;
- зафиксировать термины проекта: установка, оборудование, датчик, режим,
  отклонение, рекомендация, отчет.

Критерии готовности:

- созданы пакеты подсистем из ЛР5;
- существующие сервисы перенесены в профильные пакеты без потери
  совместимости;
- добавлены реестр подсистем, роли и словарь доменных терминов;
- добавлено краткое описание архитектуры проекта;
- baseline-тесты подтверждают новую структуру.

## 2. База данных

Цель: приблизить хранилище к IDEF1X/UML-модели и требованиям ЛР5.

Работы:

- расширить SQLite-схему таблицами пользователей, ролей, установок, оборудования,
  датчиков, показаний, планов, ресурсов, рекомендаций и отчетов;
- добавить загрузку последнего состояния после перезапуска;
- подготовить слой доступа к данным так, чтобы позднее можно было перейти на
  PostgreSQL без полной переписи UI.

Критерии готовности:

- SQLite создает справочные таблицы ролей, пользователей, установки,
  оборудования, датчиков и технологических режимов;
- SQLite создает операционные таблицы показаний датчиков, ресурсов,
  рекомендаций, отчетов, сменного журнала и лабораторных результатов;
- при инициализации БД заполняются демо-роли, установка, оборудование, датчики и
  режимы;
- каждое сохранение состояния процесса пишет агрегированную строку, строки
  датчиков и строки ресурсов;
- приложение восстанавливает последнее сохраненное состояние при запуске;
- тесты проверяют схему, справочники, запись данных и восстановление состояния.

## 3. Пользователи и роли

Цель: реализовать разграничение функций по ролям.

Роли:

- оператор;
- технолог;
- инженер КИПиА/АСУ ТП;
- руководитель;
- администратор.

Работы:

- добавить экран входа;
- ограничить вкладки и действия в зависимости от роли;
- журналировать входы и значимые операции.

Критерии готовности:

- при запуске приложение показывает окно входа;
- в БД созданы демо-пользователи для всех ролей из ТЗ;
- успешный вход формирует текущую пользовательскую сессию;
- вкладки и кнопки в главном окне зависят от роли пользователя;
- попытки недоступных действий блокируются на уровне обработчиков;
- входы и значимые операции записываются в аудит;
- тесты проверяют демо-авторизацию, аудит и матрицу прав.

## 3.1. Смена пользователя и восстановление UI

Цель: сделать пользовательские роли разными по доступу, но общими по данным
системы.

Работы:

- добавить кнопку смены пользователя без перезапуска приложения;
- записывать выход пользователя в аудит;
- загружать из БД последние события журнала при открытии главного окна;
- загружать из БД последние отклонения при открытии главного окна;
- загружать из БД актуальные статусы оборудования;
- показывать администратору последние записи аудита.

Критерии готовности:

- пользователь может сменить роль через кнопку в главном окне;
- при отмене повторного входа текущая сессия остается открытой;
- события, отклонения и статусы оборудования сохраняются между входами разных
  ролей;
- администратор видит таблицу пользователей и последние записи аудита;
- тесты проверяют чтение общей истории и восстановление статусов оборудования.

## 4. Мониторинг и тренды

Цель: довести мониторинг до уровня демонстрации технологического режима.

Работы:

- добавить таблицу параметров с единицами измерения, нормами и статусами;
- добавить графики трендов;
- улучшить симулятор источника данных;
- добавить импорт CSV/Excel как учебную замену интеграции с SCADA/DCS.

Критерии готовности:

- вкладка мониторинга показывает таблицу параметров с единицами измерения,
  нормальным диапазоном, текущим значением и статусом;
- таблица параметров обновляется на каждом тике симулятора;
- ключевые параметры выводятся на live-графиках трендов;
- графики восстанавливают последние точки из таблицы `sensor_data`;
- добавлен импорт CSV/Excel-файлов с технологическими параметрами;
- тесты проверяют формирование снимков параметров и чтение истории датчиков.

## 5. Режимы и технологические ограничения

Цель: перейти от захардкоженных порогов к справочнику режимов.

Работы:

- добавить режимы: мягкий, нормальный, жесткий, максимум керосина,
  энергосберегающий;
- хранить диапазоны параметров для активного режима;
- классифицировать отклонения как незначительные, существенные и критические;
- журналировать изменение режимов и уставок.

Критерии готовности:

- активный технологический режим хранится в БД;
- приложение загружает профиль активного режима и его уставки при старте;
- технолог и администратор могут менять активный режим в интерфейсе;
- оператор и руководитель видят режим, но не меняют его;
- таблица параметров и линии норм на графиках используют уставки активного
  режима;
- анализатор классифицирует отклонения по уставкам активного режима;
- смена режима записывается в журнал событий и аудит;
- тесты проверяют чтение режимов, смену активного режима и режимный анализ.

## 6. Журналы

Цель: покрыть журнал событий, сменный журнал и передачу смены.

Работы:

- добавить сменный журнал;
- добавить чек-лист передачи смены;
- добавить комментарии к отклонениям и действиям;
- добавить фильтры по времени, типу, важности и оборудованию.

Критерии готовности:

- добавлена вкладка сменного журнала;
- записи смены сохраняются в SQLite и восстанавливаются при открытии окна;
- оператор и администратор могут фиксировать передачу смены;
- передача смены сохраняет принимающего пользователя, итог, открытые действия и
  чек-лист;
- права на просмотр и запись разделены по ролям.

## 7. Ресурсы

Цель: реализовать учет расхода ресурсов.

Работы:

- учитывать водород, энергию, воду, катализатор и реагенты;
- показывать расход за смену и сутки;
- выявлять перерасход;
- связывать ресурсные показатели с режимом и планом.

Критерии готовности:

- ресурсные строки из `resource_usage` агрегируются за смену и сутки;
- на отдельной вкладке показаны водород, электроэнергия, охлаждающая вода и
  катализатор;
- для каждого ресурса отображаются лимиты и статус перерасхода;
- таблица ресурсов обновляется после сохранения состояния процесса и импорта;
- права доступа к разделу ресурсов заданы по ролям.

## 8. Прогнозирование и оптимизация

Цель: добавить расчетный модуль для оценки сценариев.

Работы:

- вынести расчет выхода продукции в отдельный сервис;
- добавить сценарии изменения температуры, давления, расхода сырья и водорода;
- показывать сравнение текущего и прогнозного результата;
- формировать рекомендации без прямого вмешательства в контуры DCS/PLC.

Критерии готовности:

- расчет выхода продукции вынесен в отдельный сервис `app.forecasting`;
- симулятор использует общий расчет выхода продукции;
- при аварийной остановке подача сырья снижается, а выход продукции обнуляется;
- добавлена вкладка прогнозирования для технолога, руководителя и администратора;
- сценарии показывают прогнозный выход, изменение относительно текущего режима и
  рекомендацию.

## 9. Отчетность

- сформировать отчет по отклонениям и авариям;
- сформировать отчет по ресурсам;
- добавить экспорт PDF и CSV/Excel.

Критерии готовности:

- вкладка отчетности формирует суточный, ресурсный, аварийный и сменный отчеты;
- каждый отчет сохраняется в PDF и CSV в `reports/generated`;
- факт формирования отчета сохраняется в таблицу `reports`;
- в интерфейсе отображается история сформированных отчетов;
- формирование отчетов записывается в журнал событий и аудит.
